# TD-M(PC)^2: Improving Temporal Difference MPC Through Policy Constraint

This directory is a fork of the TD-M(PC)^2 codebase
([upstream](https://github.com/DarthUtopian/tdmpc_square_public),
[paper, arXiv:2502.03550](https://arxiv.org/abs/2502.03550),
[website](https://darthutopian.github.io/tdmpc_square/)) by Haotian Lin,
Pengcheng Wang, Jeff Schneider and Guanya Shi. In this monorepo it is used to
run a TD-MPC2 baseline, with a learned world model, on the `comfree-allegro-cube`
Allegro-hand cube-reorientation task from `comfree_tdmpc`.

This copy includes only the `tdmpc_square` training code. The upstream
HumanoidBench environments, the DreamerV3, SAC (jaxrl_m), PPO and TD-MPC2
baseline code, and the pretrained low-level skill policies were removed. They
remain available in the upstream repository.

TD-M(PC)^2 (<u>T</u>emporal <u>D</u>ifference Learning for <u>M</u>odel
<u>P</u>redictive <u>C</u>ontrol with <u>P</u>olicy <u>C</u>onstraint) builds on
TD-MPC2. It adds a policy constraint so that a planning-based MBRL algorithm
can make better use of the off-policy data generated by its planner.

## Directories

- `tdmpc_square/`: training code for TD-M(PC)^2 and TD-MPC2, selected with
  `actor_mode`.
  - `tdmpc_square/config.yaml`: the Hydra config.
  - `tdmpc_square/envs/`: task wrappers, including `comfree_allegro.py`,
    `pusht.py` and `fingertips.py`.
- `scripts/check_comfree_allegro_parity.py`: parity checks for the
  `comfree-allegro-cube` wrapper.
- `evaluate/`: post-hoc analysis scripts for `pusht`.
- `EXPERIMENTS.md`: index of training runs and the commands that produced
  them.

## Installation

Use the `tdmpc-baseline` conda env described in the monorepo root README.
Inside it, install this package without dependencies:

```bash
pip install -e tdmpc_square --no-deps
```

`comfree_tdmpc` and `comfree_warp` must be importable, and `mujoco==3.6.0`
must be installed. Both come from the `tdmpc-baseline` env. The env does not
include dm_control, HumanoidBench or JAX, so only the tasks listed below run in
it. `gymnasium==0.29.1` is required: gymnasium 1.0 and later removed
`Wrapper.__getattr__` forwarding, which the env wrappers rely on.

Launch training as `python -m tdmpc_square.train` from `tdmpc-square-pearl/`,
not from `tdmpc_square/`: the import path
`tdmpc_square.tdmpc_square.tdmpc_square` only resolves from the repository
root. Logs go to `logs/<task>/<seed>/<exp_name>/`, and Hydra run directories go
to `outputs/<date>/<time>/`.

## Allegro cube baseline (comfree-allegro-cube)

### Task wrapper

`tdmpc_square/tdmpc_square/envs/comfree_allegro.py` is a thin adapter around
`comfree_tdmpc.envs.vec_allegro.VecAllegroReorientEnv`, run in-process with a
single lane. It does not reimplement anything. `comfree_tdmpc` provides:

- the dynamics (ComFree-Sim)
- the observation and reward
- goal sequencing and drop detection

The reality is `comfree_tdmpc.reality.apply_reality` with `reality_seed=12345`
and `reality_perturb=0.25`. That is the same perturbed plant that the
`comfree_tdmpc` ablation runs train and evaluate in, and it is bit-identical to
their `params_reality.npy`. The wrapper only converts CUDA tensors to numpy
float32 and adapts the vec-env API to the gym 5-tuple.

| property | value |
|---|---|
| observation | 70-dim |
| action | 16-dim in [-1, 1], mapped to absolute joint targets |
| control rate | 50 Hz |
| episode length | 120 steps |
| `seed_steps` | 1000 (set automatically) |
| `terminated` | the cube was dropped; that step's reward includes the drop penalty |
| `truncated` | time limit |
| `info["success"]` | running goal count, so pearl's `episode_success` is goals solved per episode |

Defaults are in `tdmpc_square/tdmpc_square/envs/comfree_allegro_assets/comfree_allegro.yaml`.
Override them with `+comfree_allegro.<key>=<value>`, for example
`+comfree_allegro.reality_perturb=0.0`. The keys are `episode_length`,
`reality_perturb`, `reality_seed`, `seed` and `device`.

For this task only, `eval.csv` also gets `comfree_tdmpc`'s `pi/*` and `mpc/*`
columns (return, return_std, goals_reached, dropped, length).
`<work_dir>/train.csv` gets `comfree_tdmpc`'s rolling means over the last 64
episodes, logged every 2000 steps.

### Training

Run from `tdmpc-square-pearl/`. Use `actor_mode=sac` for TD-MPC2 and
`actor_mode=residual` for TD-M(PC)^2, which is the config default.

```bash
# TD-MPC2
python -m tdmpc_square.train task=comfree-allegro-cube model_size=5 steps=1000000 seed=0 \
    actor_mode=sac exp_name=sac_1m eval_value=false eval_pi=true eval_episodes=16 \
    eval_freq=5000 save_agent_steps=[150000] disable_wandb=true

# TD-M(PC)^2
python -m tdmpc_square.train task=comfree-allegro-cube model_size=5 steps=1000000 seed=0 \
    actor_mode=residual exp_name=residual_1m eval_value=false eval_pi=true eval_episodes=16 \
    eval_freq=5000 save_agent_steps=[150000] disable_wandb=true
```

For a smoke test (a few minutes), use `steps=3000 eval_freq=1000 save_video=false`.

- **Checkpoints.** `models/final.pt` is written at the end of the run.
  `save_agent_steps=[150000]` also writes `models/150000.pt` mid-run, which is
  the same agent state a `steps=150000` run saves as `final.pt`. A killed run
  keeps only its `save_agent_steps` checkpoints.
- **Evaluation episodes.** `eval_episodes=16` matches `comfree_tdmpc`'s
  evaluation size. The config default is 1.
- **Value evaluation.** Keep `eval_value=false`. The default `true` adds 100
  Monte-Carlo rollouts (12k env steps) to every evaluation.
- **Weights & Biases.** To log there, set `disable_wandb=false
  wandb_project=<project> wandb_entity=<entity>`. Evaluation videos then render
  through `comfree_tdmpc`'s `SceneRenderer`, which needs `MUJOCO_GL=egl`.
- **Throughput.** Both actor modes train at roughly 27 env steps/s on an
  RTX 4090, plus about 33 s per evaluation (16 MPC and 16 pi episodes). For
  long runs, use `nohup setsid` or tmux.

Trained checkpoints can be evaluated in CPU MuJoCo with `sim2sim/` (see
`sim2sim/README.md`).

### Parity check

Run this from `tdmpc-square-pearl/` before long runs:

```bash
MUJOCO_GL=egl python scripts/check_comfree_allegro_parity.py
```

| check | what it verifies |
|---|---|
| (a) | The wrapper matches `VecAllegroReorientEnv` used directly: obs, reward, done flags and goal counts, per step from identical state and action, plus exactly matching seeded resets, across several episodes. |
| (b) | The wrapper's reality u is bit-identical to `comfree_tdmpc`'s reality helper, to a copy of the original inline `VecTrainer` code (16 lanes), and to `comfree_tdmpc/outputs/ablation/d_termq/params_reality.npy`, and it differs from the nominal model. |
| (c) | Through `make_env` and `TensorWrapper`: 70-dim obs, correct shapes, dtypes and bounds, `max_episode_steps == 120`, and episodes end by step 120 and carry `comfree_tdmpc`'s episode record. |
| (d) | A drop gives `terminated` (not `truncated`) and applies the drop penalty. |
| (e) | The saved `d_termq` policy, run through the wrapper for 16 episodes, solves a number of goals within the range of its logged pi evaluations. |

Check (a) cannot compare whole trajectories because the ComFree GPU sim is not
bitwise deterministic: stepping one state twice gives differences of about
1e-6. Instead, it compares each step against a noise floor measured on the fly
and allows up to 10x that floor. It can therefore fail intermittently even on
unmodified code. Rerun it before treating a failure as real. Checks (b)–(d) are
deterministic; (e) rolls the policy out on the GPU sim and uses a tolerance
around the logged evaluations.

Check (e) needs `comfree_tdmpc/outputs/ablation/d_termq/agent.pt`. It is not in
git; download it from the GitHub Release assets.

### Differences from comfree_tdmpc

The baseline deliberately runs the unmodified algorithm. Keep these
differences in mind when comparing results with `comfree_tdmpc`:

- **No terminal masking.** Pearl's trainer sets `done = terminated or
  truncated` and does not mask the TD target at a drop, the same way it handles
  HumanoidBench falls. Episodes of at most `horizon + 1` steps are dropped from
  the replay buffer.
- **Evaluation cadence.** Pearl evaluates both MPC and pi every `eval_freq`
  steps. `comfree_tdmpc` evaluates pi every 5k steps and MPC only every 25k
  steps (the `mpc_eval_every_steps` value in its ablation configs).
- **Hyperparameters.** Pearl uses its own `config.yaml` defaults: a learned
  world model, `horizon=3`, 6 MPPI iterations, 512 samples, 64 elites, 24
  policy trajectories, and `model_size=5` as passed above. None of these are
  matched to `comfree_tdmpc`'s planner or agent configuration. Only one env
  lane is used.

## Other tasks in this fork

- **`pusht`**: `task=pusht`, which needs `gym-pusht` (and `pymunk<7`, both
  listed in `requirements_tdmpc_square.txt`). Pusht-specific options in
  `config.yaml` are `delta_actions`, `delta_action_max`, `max_speed` and
  `velocity_penalty_alpha`.
- **`fingertips`**: `task=fingertips-<object>-<variant>`, e.g.
  `fingertips-cube-air`. This is a custom fingertip manipulation environment
  with objects in `envs/fingertips_assets/`, options under `+fingertips.*`, and
  `+goal_conditioned=true|false`.
- **`evaluate/`**: post-hoc analysis of `pusht` checkpoints:
  - `eval_prediction_loss.py`: world-model prediction loss
  - `visualize_q_pusht.py`: Q-value heatmaps over the action space
  - `analyze_seed_exploration.py`: coverage of the seed-phase random
    exploration

  Example:

  ```bash
  python -m evaluate.eval_prediction_loss checkpoint=<path> task=pusht
  ```

The commands used for the runs are listed in `EXPERIMENTS.md`.

## Implementation

This implementation, used to reproduce the paper's results, is largely built
on the official implementation of
[TD-MPC2](https://github.com/nicklashansen/tdmpc2), which deserves significant
credit.

Similar performance can be obtained by modifying TD-MPC2 directly. First,
change the buffer to store the planner's `mu` and `std`
(`tdmpc2/tdmpc2/trainer/online_trainer.py` and
`tdmpc2/tdmpc2/common/buffer.py`; one extra line of code). Then, in
`tdmpc2/tdmpc2.py`, pass `mu` and `std` into `TDMPC2.update_pi` and add the
policy regularization term by replacing

```python
pi_loss = ((self.cfg.entropy_coef * log_pis - qs).mean(dim=(1, 2)) * rho).mean()
```

with

```python
std = torch.max(std, self.cfg.min_std * torch.ones_like(std))
eps = (pis - mu) / std
log_pis_prior = math.gaussian_logprob(eps, std.log()).mean(dim=-1)
log_pis_prior = self.scale(log_pis_prior) if self.scale.value > self.cfg.scale_threshold else torch.zeros_like(log_pis_prior)
q_loss = ((self.cfg.entropy_coef * log_pis - qs).mean(dim=(1, 2)) * rho).mean()
prior_loss = - (log_pis_prior.mean(dim=-1) * rho).mean()
pi_loss = q_loss + self.cfg.prior_coef * prior_loss
```

An even simpler modification gives similar performance: add a BC loss directly
to the policy objective.

```python
q_loss = ((self.cfg.entropy_coef * log_pis - qs).mean(dim=(1, 2)) * rho).mean()
prior_loss = (((pis - action) ** 2).sum(dim=-1).mean(dim=1) * rho).mean()
pi_loss = q_loss + self.cfg.prior_coef * prior_loss
```
